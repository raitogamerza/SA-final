Week 8 · MVC

Model–View–Controller

  • คิดค้นโดย Trygve Reenskaug ปี 1979 ที่ Xerox PARC สำหรับ Smalltalk-76 เป้าหมายเดิมคือจัดการชุดข้อมูลใหญ่/ซับซ้อน และเชื่อม mental model ของคนกับ GUI
  • Model = ข้อมูล + business logic + กฎ ติดต่อ DB ทำงานได้เองแม้ถอด View/Controller ออก (ไม่ใช่แค่ “ตัวจัดการ DB”)
  • View = แสดงผล (render แบบ dynamic) รับ action ผู้ใช้แล้วส่งต่อให้ Controller มีหลาย view ของข้อมูลเดียวกันได้
  • Controller = ตัวกลาง รับ input → เรียก Model → เลือก View “Never handles data logic”
  • ปัญหาที่ป้องกัน: high coupling → โค้ดแข็งทื่อ ซับซ้อน ประโยชน์: Separation of Concerns, Maintainability, Testability (ทดสอบ Model ได้โดยไม่ต้องมี UI), Team Collaboration/Scalability (frontend-backend ทำขนานกัน)
  • โครงโฟลเดอร์: models/ views/ controllers/ routes/ config/ public/ เทียบเว็บพื้นฐาน HTML=content, CSS=presentation, JS=behavior
  • กรณี E-commerce: checkout ไฟล์เดียว 2,500 บรรทัด มีทั้ง SQL, ส่วนลด/ค่าส่ง, เรียก payment API, ต่อ HTML → แยกเป็น Model (Order, Cart, PaymentProcessor), View (template), Controller บาง ๆ
  • แบบฝึก C++: StudentController ถือ model และ view ไว้ View ไม่แตะ Model ตรง ๆ ถ้าเปลี่ยนจาก cout เป็นหน้าเว็บ แก้แค่ StudentView เพิ่ม GPA ต้องแก้ทั้ง 3 คลาส

  • ลดต้นทุน: Right-sizing, Auto-scaling, Reserved (สัญญา 1–3 ปี ลดได้ถึง 72%) & Spot, Budgets/alerts, Storage tiering (S3 Glacier), Architecture review

Week 10 · 7 ข้อ

Microservices & Distributed

  • Microservices: แบ่งแอปเป็นบริการเล็กอิสระตาม business capability สื่อสารผ่าน API/message broker deploy และ scale แยกได้ ใช้เทคโนโลยีต่างกันได้
  • การจัดการข้อมูล: Database per Microservice → data isolation, loose coupling, scale อิสระ (polyglot persistence)
  • ส่วนประกอบ: API Gateway (จุดเข้าเดียว route + auth), Service Registry & Discovery, Load Balancer, Docker/Kubernetes, Event Bus/Message Broker (async), Caching, Fault tolerance (circuit breaker, retry, fallback)
สถานการณ์เลือก
แอปเล็กเรียบง่าย · ทีมน้อย · ความซับซ้อนการดำเนินงานต่ำ · ไม่คาดว่าจะเปลี่ยนบ่อยMonolith
Deploy/iterate เร็ว · scalability และ fault isolation สูง · หลาย tech stack · ตลาด/ผลิตภัณฑ์เปลี่ยนเร็วMicroservices
  • คุณลักษณะระบบกระจาย: Multiple Nodes, Resource Sharing, Scalability, Fault Tolerance, Transparency (ซ่อนความซับซ้อน ดูเป็นระบบเดียว)
  • Peer-to-Peer: ทุกโหนดเท่ากัน เป็นทั้ง client และ server ไม่มี central server ทนต่อ single point of failure มี 3 แบบ Structured / Unstructured / Hybrid
  • สไตล์อื่น: Layered, Data-Centric (shared repository/blackboard), SOA (ESB, SOAP/REST), Event-Based, Client-Server (server อาจเป็นคอขวด)
  • Netflix: 700+ microservices บน AWS · Zuul=gateway · Eureka=discovery · Hystrix=circuit breaker · Chaos Monkey=resilience testing (247M สมาชิก, 15% ทราฟฟิกโลก)
  • Tesla Autopilot = Edge + Cloud hybrid (<100 ms decision loop) · CERN = Grid
Week 11 · EDA

Event-Driven Architecture

  • ส่วนประกอบสื่อสารโดยผลิตและตอบสนองต่อ event, loosely coupled
  • Event Source สร้าง event · Event เหตุการณ์/การเปลี่ยนสถานะ · Event Broker ศูนย์กลางรับส่ง · Publisher ส่ง event ไป broker · Subscriber ลงทะเบียนสนใจ event บางชนิด
  • แผนภาพ: Source1 ส่ง A, Source2 ส่ง B → Subscriber1 รับ A, Subscriber2 รับ A+B (จากทั้งสอง source), Subscriber3 รับ B
  • Event: triggering, asynchronicity, publish-subscribe, event types (UserLoggedIn, OrderPlaced), Payload = ข้อมูลแนบ เช่น PaymentReceived แนบจำนวนเงิน, event handling
  • เมื่อไหร่ใช้: หลาย subsystem ต้องประมวล event เดียวกัน · real-time · complex event processing (pattern matching, time window) · ข้อมูลปริมาณ/ความเร็วสูง (IoT)
  • ใช้จริง: การเงิน (fraud), e-commerce, โทรคมนาคม, เกมออนไลน์
  • ความท้าทาย: ความซับซ้อนเพิ่ม, ลำดับและ consistency ของ event, debugging และ tracing ยากเพราะ async + กระจาย, event latency
Week 11 · CQRS

Command Query Responsibility Segregation

  • แยก Command (เขียน เปลี่ยนสถานะ มี side effect เช่น CreateOrder) ออกจาก Query (อ่าน ไม่เปลี่ยนสถานะ เช่น GetOrderDetails)
  • UI → Command Service → Write Storage = source of truth → Sync (มักใช้ event) → Read Storage (read-optimized / materialized view) ← Query Service
  • 4 ขั้น sync: (1) เขียนลง Command DB (2) สร้าง event เช่น “Order Created” (3) Read DB ฟัง event แล้วอัปเดตสำเนา (4) Eventual Consistency อาจช้าเล็กน้อยแต่สุดท้ายตรงกัน
  • เหมาะ: query ซับซ้อน, ต้อง scale อ่าน/เขียนแยก, data model อ่าน/เขียนต่างกัน (read/write imbalance)
  • Best practices: แยก model ชัด, ใช้ async messaging กับ command, command/query เรียบง่ายไม่ปนกัน, ระบบง่าย ๆ ใช้ CQRS = overkill
  • ความท้าทาย: complexity, consistency, data synchronization, performance overhead

Week 12 · 10 ข้อ

ATAM และแนวปฏิบัติด้านสถาปัตยกรรม

  • ATAM (SEI): ประเมิน quality attributes (performance, availability, security) เพื่อลดความเสี่ยงตั้งแต่ช่วงต้นของ SDLC หา trade-off points, sensitivity points, risks
  • 3 กลุ่มผู้เข้าร่วม: Evaluation team (คนนอกโปรเจกต์ 3–5 คน) · Project decision-makers (มีอำนาจสั่งเปลี่ยน) · Architecture stakeholders (users, maintainers, performance engineers, testers, integrators, developers)
  • Risk = การตัดสินใจทางสถาปัตยกรรมที่อาจนำไปสู่ผลไม่พึงประสงค์ต่อ quality attribute · Non-risk = ไม่คาดว่าจะเกิดผลเสีย · Risk themes = จุดอ่อนเชิงระบบ

ออกแบบ Event-Driven และ CQRS

คุณเป็นหัวหน้าสถาปนิกของแพลตฟอร์มสั่งอาหาร (คล้าย GrabFood/LINE MAN) ต้องรองรับการสั่งอาหาร แจ้งเตือนร้าน จัดหาไรเดอร์ ติดตามตำแหน่งแบบ real-time และชำระเงิน
  1. ระบุ event ที่เกิดในระบบอย่างน้อย 5 event (2 คะแนน)
  2. ระบุ publisher และ subscriber ของแต่ละ event (3 คะแนน)
  3. อธิบายการใช้ CQRS แยกฝั่งเขียนคำสั่งซื้อ (สั่ง/อัปเดต) ออกจากฝั่งอ่าน (ติดตาม/ประวัติ) (3 คะแนน)
  4. ความท้าทายของ eventual consistency ในระบบนี้ และแนวทางจัดการ (2 คะแนน)
ดูแนวคำตอบข้อ 1

(a) Events

OrderPlaced, PaymentCompleted (payload: orderId, amount), OrderAcceptedByRestaurant, DriverAssigned, DriverLocationUpdated, FoodReadyForPickup, OrderDelivered, OrderCancelled

(b) Publisher → Subscriber (ผ่าน Event Broker เช่น Kafka)

EventPublisherSubscribers
OrderPlacedOrder ServicePayment, Restaurant Notification, Order Read Model
PaymentCompletedPayment ServiceOrder Service, Driver Assignment, Notification
OrderAcceptedByRestaurantRestaurant ServiceOrder Service, Customer Notification
DriverAssignedDriver Assignment ServiceTracking, Customer & Restaurant Notification
DriverLocationUpdatedDriver App / Tracking ServiceTracking Read Model, Customer App
OrderDeliveredDriver ServiceOrder, Payment (จ่ายร้าน/ไรเดอร์), Rating, History

จุดให้คะแนน: บอกว่า publisher ส่งไปที่ broker และ subscriber รับเฉพาะ event ที่ลงทะเบียน หนึ่ง event มีหลาย subscriber ได้ (loose coupling)

(c) CQRS

  • Command side: PlaceOrder, CancelOrder, UpdateOrderStatus เข้า Command Service ตรวจ business rule (ร้านเปิดไหม, สต็อก, ยอดเงิน) แล้วเขียนลง Write DB (relational, ACID) ซึ่งเป็น source of truth
  • หลังเขียนสำเร็จสร้าง event (OrderPlaced/StatusChanged) ลง event bus
  • Query side: projection ฟัง event แล้วอัปเดต Read DB ที่ออกแบบเพื่ออ่าน เช่น Redis สำหรับสถานะ/ตำแหน่งล่าสุด และ document DB/Elasticsearch สำหรับประวัติการสั่ง (materialized view รวมชื่อร้าน เมนู ไรเดอร์ไว้แล้ว)
  • Query Service ตอบหน้า tracking และประวัติจาก Read DB อย่างเดียว ทำให้ scale ฝั่งอ่าน (อ่านมากกว่าเขียนมาก) แยกจากฝั่งเขียนได้

(d) Eventual consistency

  • ปัญหา: ลูกค้าเพิ่งสั่งแต่หน้าประวัติยังไม่ขึ้น · สถานะในแอปไม่ตรงกับจริงชั่วคราว · event มาไม่เรียงลำดับ (Delivered มาก่อน PickedUp) · event ซ้ำทำให้ตัดเงินซ้ำ
  • แนวทาง: ตอบกลับ UI ด้วยผลจาก command ทันที (optimistic UI / read-your-own-writes) · ใส่ version/sequence number และใช้ partition key = orderId ให้เรียงลำดับ · consumer แบบ idempotent (เก็บ eventId ที่ประมวลแล้ว) · retry + dead-letter queue · ใช้ Saga/compensating event (เช่น PaymentFailed → CancelOrder) · monitor ความหน่วงของ projection

การประเมินสถาปัตยกรรม

มหาวิทยาลัยมีระบบลงทะเบียนเรียนออนไลน์แบบ 3-tier (web, application server เครื่องเดียว, ฐานข้อมูลเดียว) ทุกต้นภาคเรียนมีนักศึกษาราว 20,000 คนเข้าพร้อมกันในชั่วโมงแรก ระบบช้ามากจนล่มทุกปี และเคยพบนักศึกษาดูข้อมูลผลการเรียนของคนอื่นได้ ผู้บริหารต้องการประเมินสถาปัตยกรรมก่อนตัดสินใจลงทุนปรับปรุง
  1. เลือกเกณฑ์ประเมิน 3 จาก 5 ข้อ (Performance, Scalability, Reliability, Maintainability, Security) พร้อมตัวอย่างที่วัดได้ของแต่ละเกณฑ์ (6 คะแนน)
  2. อธิบายจุดประสงค์ของ ATAM และกลุ่มผู้เข้าร่วม (5 คะแนน)
  3. เลือกเครื่องมือประเมิน 1 ตัว พร้อมเหตุผลที่เหมาะกับสถานการณ์ (4 คะแนน)
ดูแนวคำตอบข้อ 2

(a) เกณฑ์ 3 ข้อ + ตัวชี้วัด (ต้องมีตัวเลข)

  • Performance: response time หน้าลงทะเบียน P99 < 2 วินาทีที่ 20,000 concurrent users · throughput ≥ 1,500 transactions/วินาที · CPU utilization < 70% ตอน peak
  • Scalability: เพิ่ม app server แบบ horizontal จาก 2 → 10 instance ได้ภายใน 5 นาทีผ่าน auto-scaling โดย response time ไม่เกินเกณฑ์ · ระบบ (ปัจจุบัน server เครื่องเดียว) ต้องรองรับโหลด 2 เท่าของ peak ปีที่แล้ว
  • Security: authorization ทุก API ตรวจว่า studentId ใน token ตรงกับข้อมูลที่ขอ (กรณีเห็นเกรดคนอื่น = broken access control) · ช่องโหว่ระดับ High/Critical จากการสแกน = 0 · ข้อมูลเข้ารหัส TLS ระหว่างทางและ at rest
  • (ทางเลือก) Reliability: availability ช่วงเปิดลงทะเบียน ≥ 99.9% (downtime ≤ ~43 นาที/เดือน) · RTO ≤ 15 นาที

(b) ATAM

  • จุดประสงค์: ประเมินว่าสถาปัตยกรรมตอบ quality attribute ที่ธุรกิจต้องการได้หรือไม่ ตั้งแต่ช่วงต้นก่อนลงทุน หา risks, non-risks, sensitivity points, trade-offs (เช่น เพิ่ม cache ช่วย performance แต่เสี่ยงข้อมูลที่นั่งไม่ตรง) แล้วสรุปเป็น risk themes เพื่อลดความเสี่ยง
  • กระบวนการ 8 ขั้น: Present ATAM → Business Drivers → Architecture → Architectural Approaches → Utility Tree → Brainstorm Scenarios → Analyze → Present Results
  • ผู้เข้าร่วม 3 กลุ่ม: Evaluation team คนนอกโปรเจกต์ 3–5 คน · Project decision-makers เช่น ผู้อำนวยการสำนักทะเบียน/ผู้บริหารไอทีที่มีอำนาจสั่งเปลี่ยน · Stakeholders เช่น นักศึกษา (users), อาจารย์, เจ้าหน้าที่ทะเบียน, developers, testers, ผู้ดูแลระบบ (maintainers), performance engineers

(c) เครื่องมือ: Apache JMeter

  • ปัญหาหลักคือระบบล่มเมื่อผู้ใช้พร้อมกันจำนวนมาก JMeter จำลอง 20,000 virtual users ยิงลำดับ login → ค้นวิชา → ลงทะเบียน ได้จริง
  • วัด response time, throughput, error rate ทำ load test และ stress test หา breaking point และคอขวด (app server เดี่ยวหรือ DB) ก่อนเปิดลงทะเบียนจริง
  • เป็น open-source ไม่มีค่า license เหมาะงบมหาวิทยาลัย และใส่ใน CI/CD ได้
  • (ถ้าเลือกด้านความปลอดภัยแทน: OWASP ZAP สแกนเว็บหาช่องโหว่อย่าง broken access control ได้ฟรี)
